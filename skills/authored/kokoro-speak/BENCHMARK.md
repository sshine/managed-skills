# Kokoro-82M: CPU vs CUDA

This is the measurement behind the CUDA option in `nix/package.nix`. It answers
two questions: how much faster is the GPU for a command that synthesizes and
exits, and where does the speed-up stop because phonemization is still on the
CPU?

## Machine

The machine that produced these numbers is the one this session runs on. The
request says it has an RTX 2080; `nvidia-smi` labels the exposed device
**NVIDIA GeForce RTX 3060 Laptop GPU** (6 GB, 80 W). I cannot verify the
hardware label from software, so I benchmarked whatever this session exposes.
If that is the RTX 2080 you bought, the table is your 2080 measurement. If the
label is right, the desktop 2080 estimate below is the better number.

| Part | Model |
|---|---|
| CPU | Intel Core i7-11700, 8 cores / 16 threads, 2.5 GHz base, 4.9 GHz boost |
| GPU (as reported) | NVIDIA GeForce RTX 3060 Laptop GPU, 6 GB, 80 W |
| Driver | 595.112.07 |

Software: onnxruntime 1.27.1, kokoro-onnx 0.6.1, Kokoro-82M v1.0, 24 kHz,
voice `af_heart`, speed 1.0. The CPU build uses the same onnxruntime version
without CUDA; the GPU build is the package in this skill with
`cudaSupport = true` and `cudaArchitectures = "86"` (the exposed GPU's compute
capability). Building that single-architecture CUDA ONNX Runtime took about 46
minutes on this 16-thread CPU; the default five-architecture package is longer,
and both are cached after the first build.

## Method

`bench/bench.py` loads the model once, warms up the first inference for each
shape, and then times repeated `Kokoro.create()` calls. The reported time is
the median of five runs up to 100 words and three runs for 300-1000 words.
Text is generated by repeating a natural paragraph, so every length is exactly
the requested number of words. The measured time includes espeak phonemization,
tokenization, chunking and all model inference, but not process start or model
load.

`bench/cold.py` measures the command a user actually runs: a fresh
`kokoro-speak` process, including Python start, model load, CUDA context setup,
synthesis and WAV write. Each number is the median of five fresh processes.

The audio duration is the length of the generated WAV. `xRT` means audio
seconds produced per wall-clock second; `RTF` is its inverse. Higher is better.

The CPU governor was set to `performance` for the warm runs and restored to
`powersave` afterwards. The machine otherwise varies by 20-40% between runs
because the governor ramps with load; without pinning it, the CPU baseline is
not comparable across runs. The cold numbers were measured under the machine's
normal `powersave` policy, since that is what a user actually experiences.

## Fresh-process latency

| Text | Audio | CPU cold | GPU cold | GPU vs CPU |
|---|---:|---:|---:|---:|
| "The build finished on all three hosts." (7 words) | 1.9 s | 1.43 s | 1.66 s | 0.86x |
| 57-word paragraph | 19.3 s | 5.79 s | 2.08 s | 2.79x |

The GPU's cold run is only 9.3x realtime on the paragraph, against ~32x warm,
because the fresh process pays the model load and CUDA context setup again.

## Where the speed-up comes from

Three things are true at once:

1. **The GPU is much faster at the model.** Warm synthesis is 5.1x faster on a
   five-word sentence, 7.3-8.7x at 20-100 words, and 10.1x at 300-1000 words.
   The GPU holds a steady **~32x realtime** once the sentence is long enough;
   the CPU degrades from 4.2x to 3.2x as chunks get longer and memory traffic
   grows.
2. **Phonemization is not the bottleneck.** espeak takes 0.02 s for 1000
   words, which is 0.2% of the GPU's 10.1 s. The headroom is in the model, not
   in G2P. (I expected the opposite before measuring.)
3. **Cold start is the GPU's tax.** A fresh CUDA session costs about 1.5-2.4 s
   against 0.6 s for the CPU build. For one short sentence the GPU is slightly
   *slower* end to end (0.86x); the crossover is roughly 20-30 words. For a
   paragraph it is already 2.8x faster, and the gap widens with length. A
   long-lived process (or a daemon) sees the warm numbers.

The controlled warm run is stable to a few percent. The uncorrected machine
(the default `powersave` governor) can be 20-40% slower on the CPU side, which
is why the governor is pinned for the comparison.


## RTX 2080 estimate

`nvidia-smi` in this session labels the device **NVIDIA GeForce RTX 3060
Laptop GPU** (6 GB, 80 W). You are confident the machine is the RTX 2080 you
bought; software cannot verify the label from here, so the table above is the
measurement of whatever GPU this session actually exposed. **If that is your
RTX 2080, the measured numbers are already the 2080 numbers.** If the label is
right and the card is the 80 W laptop 3060, the desktop 2080 should be faster
still; the estimate below covers that case.

The RTX 3060 Laptop has 3840 CUDA cores but only an 80 W budget and 336 GB/s
of memory bandwidth. A desktop RTX 2080 has 2944 CUDA cores and 184 tensor
cores, 10.1 TFLOPS FP32, 448 GB/s and a 215 W budget. For a small fp32 ONNX
model the two are closer than the core counts suggest: the 2080 has more
bandwidth and a much larger power budget, the 3060 Laptop has more CUDA cores
and newer per-core scheduling. A reasonable estimate is that the desktop 2080
would be **1.2-1.5x the CUDA throughput measured here**, with the upper end for
long texts where the model is compute- and bandwidth-bound and the lower end
for short texts where session setup dominates.

That puts the desktop-2080 warm numbers at roughly:

| Words | Speed-up over CPU | GPU xRT |
|---:|---:|---:|
| 5 | 6.1-7.6x | 26-32x |
| 1000 | 12-15x | 39-49x |

The cold-start penalty stays in the same 1.5-2.5 s range, so a one-sentence
command is still roughly parity with the CPU; a paragraph cold run should be
about 3-3.5x faster. If the card is a laptop 2080 Max-Q (80 W, 1095 MHz), the
estimate is closer to the measured 3060 and may even be slightly slower in
fp32.

## Apple Silicon: M5 Pro/Max speculation

This skill is x86_64-linux only. An M-series port would need a different espeak
library package and either ONNX Runtime's CoreML execution provider, a native
CoreML/ANE pipeline, or MLX (`mlx-audio`). The numbers below are therefore
speculation about a port, not a benchmark of this package.

Published Kokoro-82M measurements from an optimized CoreML/ANE pipeline
(`mattmireles/kokoro-coreml`, October 2026) and MLX on the same machines:

| Pipeline | Device | 27.4 s of audio | x realtime |
|---|---|---:|---:|
| CoreML + ANE/GPU hybrid | M1 Mac mini | 309 ms | 89x |
| CoreML + ANE/GPU hybrid | M2 Ultra | 159 ms | 172x |
| MLX | M1 Mac mini | 3.02 s | 9x |
| MLX | M2 Ultra | 0.77 s | 36x |

The relevant top M5 is the **M5 Max**: 18 CPU cores (6 super + 12
performance), a 32- or 40-core GPU with a Neural Accelerator in every core,
a 16-core Neural Engine (42 TOPS), and 460-614 GB/s of unified memory. Apple
claims about 4x the peak GPU AI compute of the M4 Max, and 1.2x the raster GPU
performance.

Putting those together:

- **Optimized CoreML/ANE pipeline (best case):** the M2 Ultra does 27.4 s in
  159 ms. The M5 Max has fewer GPU cores (40 vs 76) but a newer architecture,
  a faster Neural Engine (42 vs ~32 TOPS) and the same hybrid idea. A 30 s
  clip in **~0.1-0.2 s, or 150-250x realtime**, is a reasonable speculation.
  The measured CUDA path is 21-33x warm, so this is roughly **5-10x faster
  than the NVIDIA/ONNX approach** — with a much more specialized pipeline.
- **MLX (easiest Mac port):** M2 Ultra reaches 36x realtime. The M5 Max's
  40-core GPU is newer but has half the cores, so expect roughly **20-60x
  realtime**, depending on how well MLX uses Metal 4's tensor APIs. That
  overlaps the measured CUDA range; it could be similar or modestly faster.
- **ONNX Runtime + generic CoreML EP (closest to this skill's code):** the
  generic execution provider does not split the graph across ANE and GPU the
  way the specialized pipeline does, and may fall back to CPU for some ops.
  Expect **10-40x realtime**, which overlaps the measured CUDA path rather
  than clearly beating it; the software path, not the M5 Max, is the
  bottleneck.
- **CPU-only on an M5 Max:** single-core performance is well above the
  i7-11700, so expect maybe 1.5-2.5x the CPU column (roughly 5-8x realtime),
  but the GPU/CoreML path is the one worth taking.

The CoreML reference numbers start from token IDs; add G2P and text handling
before comparing directly. That addition is small compared with these times
(espeak takes 20 ms for 1000 words in the measured build).

For comparison, an RTX 2080 on CUDA is likely 1.2-1.5x the numbers above
(roughly 26-50x realtime). A well-optimized M5 Max CoreML port would beat that
comfortably; an MLX or ONNX Runtime CoreML port could land in the same range
as the NVIDIA card, or below it if the execution provider falls back. The
lesson is that for an 82M model, the runtime and the graph split matter more
than the peak TOPS.

## Reproduce

```bash
# Warm synthesis, CPU and CUDA (CUDA first builds ONNX Runtime).
nix run .#kokoro-bench-cpu  -- --label cpu  --json-out /tmp/cpu.json
nix run .#kokoro-bench-cuda -- --label cuda --json-out /tmp/cuda.json
nix shell nixpkgs#python3 -c python3 bench/compare.py /tmp/cpu.json /tmp/cuda.json

# Fresh-process latency (replace the wrapper path with the build output).
nix shell nixpkgs#python3 -c python3 bench/cold.py \
  --wrapper ./result/bin/kokoro-speak --label cuda --device cuda \
  --text "The build finished on all three hosts." --runs 5
```
